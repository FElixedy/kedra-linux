# Milestone baselines

A baseline is one immutable answer to "what, exactly, is this milestone?" --
which source commits, which package artifacts, which repository database and
which ISO were built and accepted **together**.

`m0-baseline.json` and `m0-baseline.md` in this directory are that answer for
Milestone 0. They are generated by `bin/kedra-baseline-manifest`, not written by
hand: commits come from git, hashes from `sha256sum`, package versions from each
package's own `.PKGINFO`, tool versions from `pacman`. Only the acceptance
results are typed in, because they are observations no script can make for
itself.

## Why this exists

Milestone 0 passed its acceptance run and was still not one baseline.

`kedra-calamares` had been published as `3.4.2-1`, then republished during
development under the *same* version after the source had moved on. The result:

| | `bootloaderEntryName` |
|---|---|
| kedra-calamares source at HEAD | `Kedra` |
| the published `3.4.2-1` artifact | `Kedra Linux` |
| the tested ISO | `Kedra Linux` |

which is why the first installed system's boot menu read `Kedra Linux Linux`.
Because `pkgrel` had not moved, nothing in pacman could tell the two builds
apart. Source, artifact and image each described a different Milestone 0.

Separately, the live ISO shipped `[cachyos]` with `SigLevel = Optional TrustAll`
-- signature verification effectively off for the CachyOS repositories, on the
medium that installs the user's machine -- and the validation that was supposed
to catch that only searched for the string `SigLevel = Never`.

M0.1 fixed both, rebuilt everything from committed sources, re-ran the full
end-to-end acceptance, and recorded the result here.

## Tag scheme

**`m0`** -- the same tag name in every Kedra repository, pointing at the exact
commit recorded for that repository in the manifest.

| | |
|---|---|
| Name | `m0` (not `milestone-0`, not `v0`) |
| Repositories | `kedra-hooks`, `kedra-keyring`, `kedra-repo`, `kedra-calamares`, `kedra-iso` |
| Points at | the commit in `sources.<repo>.commit` in `m0-baseline.json` |
| Created | only after the full acceptance run passed |

One name across five repositories means `git checkout m0` reconstructs the whole
milestone without consulting anything. Later milestones follow the same pattern:
`m1`, `m2`.

`kedra-calamares` carries upstream Calamares' own `v*` release tags and a
`3.1-beta2`; a bare `m0` cannot collide with those, which is part of why the
`v`-prefixed form was not chosen.

Tags are additive. No history is rewritten to create one, and a tag is never
moved: if a baseline turns out to be wrong, the next one gets its own tag.

## Reading the manifest

```sh
jq -r '.sources | to_entries[] | "\(.key) \(.value.commit)"' baseline/m0-baseline.json
jq -r '.packages[] | "\(.name) \(.version) \(.sha256)"'       baseline/m0-baseline.json
jq -r '.iso | "\(.filename) \(.sha256)"'                      baseline/m0-baseline.json
jq -r '.acceptance_results'                                   baseline/m0-baseline.json
```

`iso.built_from_commit` records the commit the image was actually built from,
which is not automatically the commit the tag points at -- the generator diffs
every path that can affect the image between the two and refuses to write a
manifest if the ISO is not reproducible from the tag. `iso.provenance` says
which case applies.

## What is deliberately not in here

No private key material. The repository signing key's **fingerprint** is
recorded, because verifying the baseline is impossible without knowing which key
to expect, and a fingerprint is public by construction. The signing key itself
is a development key held outside every git tree (`kedra-repo/docs/signing.md`);
replacing it with a production identity is Alpha work, not M0.
